## The 28 zero-count boards, classified

A zero is not empty until the fetch evidence says it. The evidence is each board's own entry
in its adapter rollup row's `details` — **which the drain tool was not reading**, so all 25
provider boards inherited the rollup's totals and read `rollup_only`. Reading the detail
decides all 28:

| state | boards | evidence |
|---|---:|---|
| collected | 3 | `justplay-gmbh` 1, `scape` 1, `bandainamco-nexus` 2 rows kept |
| fetched_empty | 17 | greenhouse: asked, 112–713 ms spent, `fetchedCount: 0`, no error |
| unknown (`no_openings`) | 8 | ashby: "no jobs extracted from ashby board html", `browserFallbackRecommended: true` |

The greenhouse 17 (`taketwo`, `applovin`, `kambi`, `adjustjobs`, `unknownworlds`,
`tripwireinteractive`, `growe`, `keensoftwarehouseas`, `fastspring`, `2kvegas`,
`crystaldynamics`, `dots`, `firaxis`, `inzoistudio`, `pmstudios`, `pubgmadison`, `kano`) were
genuinely asked and returned nothing. The ashby 8 (`supercell`, `volka`, `i3d`, `sorare`,
`block-labs`, `fnatic`, `justplay-gmbh` was collected, `scape` was collected) — of the eight
zeros, all are the "no jobs extracted from ashby board html" shape, and every one of them
carries `browserFallbackRecommended: true`. That is the browser lane's population, not a dead
board.

**Two hrmos boards are a real extraction gap.** `gree` and `happinet` were asked
(`cacheDecision: run_now`, 1,599 ms and 1,193 ms spent) and extracted nothing, while a forced
per-board fetch collects **20** and **15** rows from the same URLs. So the runtime's static
path and a fresh fetch disagree on the same page — a defect to settle, not a board to blame.

**No board in this set is claimed as empty on a rate-limited read.** An earlier pass of this
analysis ignored the HTTP status and reported 32 rows for `taketwo` and 43 for `applovin`; a
control-first re-run then showed `greenhouse 2k → HTTP 200 with 0 rows` and
`coverage_verify`'s own control returning `[2, 0]` for `grover`, so the provider APIs were
degraded at that moment and those numbers are **withdrawn**. The classification above uses no
network at all — it is the run's own recorded evidence.

## Browser-fallback demand, re-measured

The ledger's 988-of-1,032 figures came from the 0.3.008 full live run; the v7 curated replay
showed only 71 attempts. The v8 full-seed run:

```
runtime.browserFallbackDemand = {attempts: 843, refused: 716, servedWithHtml: 121, servedEmpty: 6}
runtime.browserFallbackEnabled = true, cap = 12, cooldownMinutes = 30
```

716 of 843 refused. The breaker is **run-level, not per-source** (`pipeline_source_loop.py:250`),
and it only trips `disabled_until_at` when `is_browser_fallback_environment_error(error)` is
true — so the global cooldown is correct for a broken browser. What is missing is the
distinction inside `demand_served_empty`, which lumps "the browser is broken" together with
"this page rendered empty", plus the refusal reason. That is BF2's real scope, and it is why
the 403 population cannot be classified yet. The 8 ashby boards above are the concrete
population BF2 has to explain.

## P4 — Deadline-capacity correctness (separate behavior change)

**Status: ACCEPTED** (P2/P3 re-audit passed 2026-10-13; acceptance signed off by the user 2026-10-13: "Accept P4 contract, proceed to P5"). Complete and locally verified; stays in the working tree; may proceed to P5. No commit/push/release without further explicit authorization.

**Decision (user):** eliminate false deadline failures only — add the missing capacity terms so valid work never hits a synthetic deadline, while pathological/dripping batches stay bounded promptly. A net-lengthening of the deadline for multi-request/family-constrained valid work, as tight as possible while never truncating a legitimate batch.

**The defect (measured):** both deadline formulas assume each row makes one `timeout_s` request at full `effective_concurrency`:
```python
total_deadline_s = per_row_s * (rows/effective_concurrency) + per_row_s
```
Two omitted terms make this an understatement. (1) **Requests-per-row > 1:** a probe row is `[endpoint_url, *fallback_probe_urls]`, so adapters with fallbacks make ≥2 requests; Workday's structured probe is a POST with `retries=2`/`backoff_s=1.0` plus a timeout-retry attempt, each sub-request with its own `call_timeout_s`, so a legitimate row can exceed `timeout_s` → synthetic deadline failure on valid Workday/fallback batches. Homepage rows are single-fetch, so `http_batch`'s default is unaffected. (2) **Family-constrained concurrency:** the probe funnels candidates through per-family bucket semaphores before the total sem, but `effective_concurrency = total` ignores the family cap; a family-saturated batch (e.g. provider ~24 of 40 lanes) cannot use all lanes, so a total-lane deadline overstates realizable throughput.

**The fix (implemented; probe path only, `http_batch` unchanged):**
1. `probe.py:probe_row_timeout_units(candidate, timeout_s)` returns the per-row ceiling in `timeout_s` units — `len(_probe_urls) × attempts` for ordinary adapters (default 2, legacy 3), and for a Workday board with a listing URL the structured POST budget `(4 × max(5, timeout_s) + 2s backoff)/timeout_s`. A ceiling, never truncates valid work, computed before any request.
2. `run_bounded_probe_batch_async(..., requests_per_row: int = 1)` — default 1 keeps non-probe-aware callers at the previous bound; the deadline becomes `row_work_s × (rows/effective_concurrency) + row_work_s`.
3. `probe_candidates_async` computes `requests_per_row` = max over candidates and threads it in (entry used by browser_recovery/gamedevmap/active_audit).
4. Family-constrained `effective_concurrency` is now `min(total, aggregate_bucket_capacity, len(candidates))`, where `aggregate_bucket_capacity = Σ_bucket min(limits[bucket], rows in bucket)`. A static-heavy wave genuinely runs at most `static` (16) lanes, not `total` (40); provider-heavy waves keep 40 and are unchanged.

**Hard constraints (held):** per-request budgets/caps, host/static limits, verdict order, and error isolation stay fixed. Pathological work stays bounded: a dripping host's each request is cut by its per-call budget, so a dripping row consumes at most `requests_per_row × timeout_s`, exactly what the scaled deadline covers; the cutoff lengthens by `requests_per_row` (the necessary cost of not truncating valid multi-request work) but is never unbounded. The performance measure that matters is walls with all work correctly settled, not a status badge.

**Acceptance contract (requires explicit user sign-off before this patch merges):** measured before/after (failing-before oracle): OLD (`requests_per_row=1`) 4.4 s / 22 calls / 0-of-5 valid rows complete (truncated by the single-request deadline on a wave needing 5 s); NEW (`requests_per_row=5`) 5.2 s / 25 calls / 5-of-5 complete. Expected corrections: a valid Workday/fallback batch previously hitting `deadline_exceeded` now completes (fixture proves the mechanism; a live Workday batch confirmation needs production data — see P6); no healthy fixture is truncated (pathologically-scoped oracle); every still-failing live outcome has an explained cause (real saturation/drip), not the capacity underestimate. **Contract change to call out:** the pathological drip cutoff grows by `requests_per_row` (from `timeout_s` to `requests_per_row × timeout_s` per row) — the deliberate, bounded cost of the "eliminate false deadline failures only" direction; static-heavy waves' pool/lanes receipt now reports the real family cap (16) instead of `total` (40), provider-heavy waves unchanged.

**Experiment + gate (implemented and locally verified):** failing-before oracle (valid 5×5 wave trips the single-request deadline and completes with `requests_per_row=5`); unit seam (Workday bound > plain-row bound, both ≥1); pathological control (hanging row cut off promptly, bound scales but is not unbounded); regressions green (existing probe runtime/lifecycle suites, full `tests/source_discovery` 814 passed / 1 skipped; `http_batch` untouched). Deterministic sleep-based proof is the acceptance evidence; live Workday-batch confirmation is a P6 handoff item needing production data.

Owners: `src/source_discovery/probe_runtime.py`, `src/source_discovery/probe.py`, `tests/source_discovery/test_probe_deadline_capacity.py`.

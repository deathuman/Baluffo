# 0.2.0 Deferred Desktop UX Polish Implementation Plan

## Summary

This plan captures deferred desktop UI and main-flow polish items from the visual inspection pass. It is intentionally more implementation-oriented than the broader release-readiness plan: each item explains what should change, why it matters, and how to evaluate the result.

The scope is desktop-first. Mobile layout work is explicitly out of scope for this pass.

This plan does not change release metadata, app version, changelog, tags, or artifacts.

## Implementation Checklist

1. [x] Redesign the Jobs list row hierarchy into a dense desktop table-hybrid row.
2. [x] Replace the compact `+` / `x` save affordance with clearer icon save/saved states.
3. [ ] Separate Jobs browsing controls from operational update controls.
4. [x] Make quick filters look like intentional presets and clarify the `Customize` control.
5. [ ] Move `Run Discovery + Fetch + Sync` out of the primary browsing toolbar.
6. [ ] Reduce Saved Jobs phase-control prominence and move advanced lifecycle controls behind context.
7. [ ] Move Saved Jobs notes, files, and history behind a clearer details drawer.
8. [ ] Make Saved Jobs attachment/note state quieter unless action or error is needed.
9. [ ] Replace bare Saved Jobs remove `X` with clear remove and undo/confirmation behavior.
10. [ ] Treat Saved Jobs activity timeline as a real drawer with meaningful defaults.
11. [ ] Collapse Admin advanced/destructive bulk actions by default.
12. [ ] Demote bridge status on user-facing pages and keep detailed bridge diagnostics in Admin.

## Design Principles

- The Jobs page should feel like a job browser, not an operations dashboard.
- Each job row should have one clear reading path: role, company, location/work mode, metadata, actions.
- Advanced, diagnostic, or destructive controls should be visible only when the user intentionally enters that mode.
- Saved Jobs should progressively disclose application-management features after the user selects or expands a saved job.
- Admin can stay utilitarian, but it should not look broken, unsafe, or accidentally user-facing.
- No new dependencies should be added for this polish pass.

## Jobs Page: Main List Visual Hierarchy

### Current problem

The Jobs list reads as a dense data table. `Position`, `Company`, `Sector`, `City`, `Country`, `Contract`, and `Type` receive nearly equal visual weight. This makes the first scan harder because the user has to reconstruct the job from columns instead of reading a coherent listing.

### Motivation

The release-facing Jobs page should optimize for fast human scanning. A user needs to answer: what is the role, who is hiring, where is it, is it remote/on-site, and what can I do next? Sector, contract, freshness, lifecycle, and source state are useful but should not compete equally with title and company.

### Proposed implementation

Implemented as a dense desktop table-hybrid row rather than a card row. The accepted layout preserves high result density while making the title scan path stronger:

```text
Senior Technical Artist                         Thera Bytes        Netherlands        Full-time   Remote   [+]
Game                                                               Amsterdam
```

Final row behavior:

- Show freshness inside the position line; unknown freshness uses an empty muted ring.
- Show the job title as the strongest text in the row.
- Show sector as quiet secondary text under the title.
- Keep company as a separate column next to position.
- Show location as country over city in one column.
- Keep `Contract` and `Type` as fixed-width centered pill columns.
- Use a compact icon save control with accessible labels.
- Keep row click/open behavior; do not add a separate `Open` button in the dense default row.

Primary files likely involved:

- `frontend/shared/components/JobRow.js`
- `frontend/jobs/app/runtime/list-view.js`
- `styles/jobs.css`

### Acceptance criteria

- First visible job rows can be understood by scanning position, company, location, contract, type, and save columns.
- Title is visually dominant and sector is secondary.
- Metadata is present but secondary.
- `Unknown` does not appear as a prominent row value when better data exists.
- Row density remains suitable for desktop browsing.

## Jobs Page: Save and Open Actions

### Current problem

The save action is a small `+` or `x`. It is low-affordance and can be confused with expansion, deletion, or row manipulation. The row itself may be clickable, but the UI does not clearly communicate how to open the original job post.

### Motivation

Saving and opening are core actions. A release-facing app should not rely on ambiguous symbolic controls that require interpretation. Clear icon state, title text, and accessible labels reduce risk when users are browsing many similar listings quickly without adding full-width row actions.

### Implemented direction

Implemented as a compact icon control instead of full text buttons so the dense Jobs row keeps its result density.

Final behavior:

- Unsaved state uses a `＋` icon with `Save job` accessible label and title.
- Saved state uses a `✓` icon with `Job saved` accessible label and `Saved` title.
- The save control has distinct outlined/tinted states and stays in a fixed-width `Save` column.
- The separate visible `Open` button was intentionally rejected for this dense row; row click/open behavior remains the opening affordance.

Interaction details:

- Clicking the save icon should not open the job.
- Clicking the row-open target should open the original posting.
- Saved state should update in place without shifting the row layout.
- Disabled save state should explain why, for example guest/offline profile state.

### Acceptance criteria

- A user can identify save state from the icon, visual state, and accessible label.
- Saved rows do not use `x` as the primary unsave indicator.
- The save control does not steal excess row width from job information.
- Row click/open remains available for opening the original job posting.

## Jobs Page: Browsing Controls vs Operational Controls

### Current problem

`Refresh Jobs` and `Run Discovery + Fetch + Sync` sit near filters and browsing controls. This makes the page feel like an internal control panel rather than a finished desktop job browser.

### Motivation

The main Jobs page should not ask ordinary users to understand the ingestion pipeline. Operational controls are still useful, but they belong behind an explicit update or admin mode. This reduces accidental use and improves first impression.

### Proposed implementation

Split the controls into three levels:

1. Browsing controls.
2. Feed freshness controls.
3. Advanced operations.

Browsing controls:

- Filters.
- Search.
- Sort.
- Quick filter presets.
- Active filter summary.

Feed freshness controls:

- Keep a lightweight `Refresh jobs` control if it only reloads current local data.
- Show last loaded or last updated state if already available.
- Use copy such as `Refresh local jobs` if the action does not run the full pipeline.

Advanced operations:

- Move `Run Discovery + Fetch + Sync` into an `Advanced update` disclosure or route it to Admin.
- The button should not appear in the primary filter toolbar.
- The advanced area should explain what the operation does before the user starts it.
- If kept on Jobs, label it as operational: `Update job database` with explanatory text.

Preferred release implementation:

- Keep `Refresh jobs` as a small secondary control near feed status.
- Move `Run Discovery + Fetch + Sync` behind an `Advanced update` disclosure.
- Include a link or button to Admin for full pipeline controls.

Suggested copy:

- Primary feed status: `Loaded 29,761 jobs`
- Secondary status: `Local cache`
- Refresh action: `Refresh local jobs`
- Advanced disclosure: `Advanced update`
- Advanced action copy: `Run discovery, fetch, and sync`
- Helper text: `Use this when you want to update sources and rebuild the local job database. This can take longer than a normal refresh.`

### Acceptance criteria

- The first visible toolbar reads as a browsing toolbar.
- Pipeline controls are not visually equal to filters/search.
- The advanced operation has explanatory copy before execution.
- Admin remains the canonical place for detailed pipeline state.

## Jobs Page: Quick Filters and Customize

### Original problem

Quick filters are useful, but they currently sit close to regular filters without enough visual distinction. `Customize` is ambiguous because it does not clearly communicate whether it customizes quick filters, visible filters, layout, or presets.

### Motivation

Quick filters should feel like curated shortcuts. `Customize` should either control a clear feature or be renamed so users understand it before clicking.

### Implemented direction

Implemented as a named preset strip:

- The strip is labelled `Presets`.
- Positive quick filters render as preset pills with active/inactive states.
- `Clear filters` is visually separated from the positive preset pills.
- Active filters still appear in the filter summary below the strip.

Clarified customization:

- The action is now `Customize presets`.
- The panel is labelled `Customize presets` and its title is `Show presets`.
- `Reset defaults` is disabled when default presets are already shown, enabled after preset visibility changes, and disabled again after reset.

Release copy:

- Preset strip label: `Presets`
- Presets: `Remote`, `New`, `No internships`, `Netherlands`, `Technical Artist`
- Customization action: `Customize presets`

Behavior details:

- Preset pills should toggle filters without surprising resets.
- `Clear filters` should be visually separate from the positive preset pills.
- Active filters should still appear in the filter summary.

### Acceptance criteria

- Quick filters are visibly different from form controls.
- `Customize` no longer feels ambiguous.
- `Clear filters` is not mistaken for a normal preset.

## Saved Jobs: Phase Lock and Lifecycle Controls

### Current problem

`Override Phase Lock` is visible and prominent. It reads like an internal debugging or power-user control, which is not appropriate as a top-level release-facing action.

### Motivation

Application phase management should feel safe and intentional. Override controls are useful only when a specific transition is blocked. Showing them globally creates anxiety and suggests the product has fragile state.

### Proposed implementation

Remove global prominence from `Override Phase Lock`.

Use contextual override instead:

- Keep normal phase progression visible.
- If the user attempts a blocked transition, show a small inline explanation.
- Offer a contextual `Override this transition` action only inside that blocked-state message.
- Require a deliberate second action if the override can create inconsistent lifecycle history.

Suggested blocked-transition copy:

```text
This phase change is normally locked because it skips an earlier application step.
```

Suggested contextual action:

```text
Override for this job
```

Recommended state model:

- No global override armed state in the normal toolbar.
- Override state scoped to one job and one attempted transition.
- Override state expires after completion, cancellation, or row collapse.

### Acceptance criteria

- `Override Phase Lock` is not visible as a top-level Saved Jobs action.
- Users see override controls only after a blocked transition creates context.
- Normal phase changes remain easy.
- Risky phase changes explain why they are risky.

## Saved Jobs: Row Progressive Disclosure

### Current problem

Saved rows include many concepts at once: phase bar, details toggle, notes, files, history, lifecycle, missing chips, reminder state, and update hints. The result is powerful but visually heavy.

### Motivation

Saved Jobs should help users manage applications without making every row feel like a full dashboard. The row should first answer: what is this job, what phase is it in, and what needs attention?

### Proposed implementation

Use a two-level saved row:

1. Collapsed row.
2. Expanded details drawer.

Collapsed row content:

- Title.
- Company.
- Clean location/work mode.
- Current phase summary.
- Due-soon reminder chip only when relevant.
- Missing-info chip only when actionable.
- Primary next action, if one exists.

Collapsed row should not show:

- Notes textarea.
- Attachment uploader.
- Full history.
- Full phase transition controls.
- Full lifecycle debug details.

Expanded details drawer:

- Show phase controls.
- Show notes.
- Show files.
- Show history.
- Show source/lifecycle details.

Recommended collapsed layout:

```text
Senior Technical Artist                   Applied        [Details]
Thera Bytes · Remote                      Reminder due soon
```

Recommended expanded tabs:

- `Overview`
- `Notes`
- `Files`
- `History`

If keeping current tabs:

- Keep `Notes`, `Attachments`, and `History`.
- Add a small `Overview` section above tabs for phase and reminder controls.

### Acceptance criteria

- Collapsed saved rows are significantly calmer than expanded rows.
- Notes/files/history are not rendered as primary row content.
- Full phase controls are visible only after expansion.
- Important warnings still surface in collapsed state.

## Saved Jobs: Notes, Files, and History Drawer

### Current problem

The details toggle exists, but the content still feels like a collection of table sections. Notes, files, and history need clearer containment and intent.

### Motivation

A drawer pattern makes the transition from scanning to managing explicit. It helps the user understand that they are opening a workspace for one saved job.

### Proposed implementation

Replace the current details area presentation with a clearer drawer-like region inside the expanded row.

Drawer header:

- Repeat job title in compact form.
- Show current phase.
- Include a `Close details` action.

Drawer body:

- Use tabs or segmented buttons for `Notes`, `Files`, and `History`.
- Keep each panel focused on one task.
- Show empty states with action-oriented copy.

Notes panel:

- Show textarea.
- Show save state only when saving, unsaved, saved recently, or failed.
- Use quiet text for normal saved state.

Files panel:

- Show upload control.
- Show max file limits as helper text.
- Show empty state: `No files attached yet.`

History panel:

- Show latest activity first.
- Avoid showing refresh as a primary action unless stale data is known.

### Acceptance criteria

- Expanded details feel like a contained workspace.
- The user can close details without losing row context.
- Empty states are readable and not diagnostic-looking.

## Saved Jobs: Quieter Attachment and Note Save State

### Current problem

Attachment and note state can add visual noise even when nothing needs attention.

### Motivation

Persistence indicators should reassure users without competing with job and phase information. They should become prominent only when data is unsaved, saving, failed, or requires action.

### Proposed implementation

Use state-specific visibility:

- Hidden or very quiet when saved and idle.
- Inline subtle text for `Saving...`.
- Temporary confirmation for `Saved`.
- Persistent warning for `Could not save`.
- Persistent warning for attachment upload failure.

Recommended note state behavior:

- Idle saved state: no badge or small `Saved` text in muted color.
- During debounce or request: `Saving...`
- On success: `Saved just now`, then fade to quiet.
- On failure: `Could not save. Retry`

Recommended attachment state behavior:

- Idle with no files: `No files attached yet.`
- Uploading: progress or `Uploading...`
- Success: short confirmation.
- Failure: visible error with retry/remove action.

### Acceptance criteria

- Normal saved state does not dominate the row.
- Errors are clearly visible.
- Saving/uploading states are not ambiguous.

## Saved Jobs: Remove Action

### Current problem

Saved job removal uses a bare `X`, which can look like close, delete, dismiss, or remove depending on context.

### Motivation

Removing a saved job is destructive from the user's point of view. It should be understandable and recoverable enough that users do not hesitate or accidentally remove rows.

### Proposed implementation

Replace the bare `X` with one of these release-safe patterns:

Preferred pattern:

- Use a visible `Remove` button in expanded/details state.
- Use a compact icon-only button in collapsed state only if it has a clear accessible label and confirmation/undo.

Undo behavior:

- On remove, optimistically hide the row.
- Show a toast or inline message: `Removed saved job. Undo`
- Undo restores the job and its local state.

If undo is too large for this pass:

- Ask for confirmation before removal.
- Confirmation copy should name the job.

Suggested confirmation copy:

```text
Remove "Senior Technical Artist" from saved jobs?
```

### Acceptance criteria

- No bare `X` is used as the only visible removal affordance.
- Removal intent is clear before action completes.
- Either undo or confirmation protects against accidental removal.

## Saved Jobs: Activity Timeline Drawer

### Current problem

The activity timeline appears as persistent side UI even in guest or empty states. It can show `Selected: none`, which feels like an implementation detail rather than user-facing state.

### Motivation

Timeline is useful when a user is managing saved jobs. It is distracting before there is saved-job context. Treating it as a drawer makes it intentional and prevents empty diagnostic-looking UI.

### Proposed implementation

Closed/default behavior:

- Guest state: timeline closed and not visually emphasized.
- Signed-in empty state: timeline closed.
- Signed-in with saved jobs: timeline closed by default unless user previously opened it.

Open affordance:

- Use a labeled button: `Activity timeline`.
- Place it near saved-job workspace controls, not as a floating mystery control.
- If there are unread/recent events, show a small count badge.

Drawer content:

- Header: `Activity timeline`
- Close action: `Close`
- Scope control.
- Activity list.
- Clear empty state.

Default scope behavior:

- If a saved job is selected, default to selected job activity.
- If no saved job is selected, default to all activity.
- Do not show `Selected: none` as primary text.

Replacement copy:

- No selected job: `Showing all saved-job activity.`
- Selected job: `Showing activity for this job.`
- Empty timeline: `No activity yet. Changes to phases, notes, and files will appear here.`

### Acceptance criteria

- Timeline is closed in guest and empty states.
- Opening and closing the timeline is explicit.
- Timeline scope copy reads as user-facing language.
- `Selected: none` is not shown as a primary state.

## Admin Polish: Advanced and Destructive Controls

### Current problem

Admin shows many operational controls at once, including bulk actions and destructive or high-impact source controls. This contributes to a raw control-panel feeling.

### Motivation

Admin can be powerful, but high-impact actions should not be visually casual. Collapsing destructive actions by default reduces accidental clicks and improves readability.

### Proposed implementation

Group Admin source controls into visible sections:

1. Review queue.
2. Safe actions.
3. Advanced actions.
4. Destructive actions.

Default visibility:

- Show review queue and safe actions.
- Collapse advanced actions.
- Collapse destructive actions.

Bulk actions:

- Keep `Approve` and low-risk review actions visible when sources are selected.
- Move delete, demote, restore rejected, and similar high-impact actions behind an `Advanced bulk actions` disclosure.
- Add short explanatory copy before destructive actions.

Button states:

- Replace repeated generic `Working...` text with action-specific labels where possible.
- If a whole section is locked by a running pipeline, show one section-level busy message and keep individual button labels stable.

Suggested copy:

- Disclosure: `Advanced bulk actions`
- Destructive section note: `These actions change source registry state and may affect future job imports.`

### Acceptance criteria

- Destructive bulk actions are not visible by default.
- Running/busy state does not make every button look broken.
- Admin remains efficient for power users after expanding advanced controls.

## Bridge Status Visibility

### Current problem

User-facing pages show `Admin Online`, which is technically useful but visually exposes implementation details. The bridge status is more relevant to Admin than to normal browsing.

### Motivation

Release-facing pages should not foreground local bridge internals. Users need to know when a user-facing feature is available, not whether the internal admin bridge is online.

### Proposed implementation

Jobs and Saved pages:

- Demote bridge status to a quiet footer/status area.
- Rename `Admin Online` to user-facing copy if it remains visible.
- Prefer `Local services ready` or hide it behind diagnostics.
- Keep Admin navigation available, but do not style bridge status as a primary badge.

Admin page:

- Keep detailed bridge state visible.
- Show bridge status in the Admin header or health section.
- Include detailed diagnostics only in Admin.

Recommended release behavior:

- Jobs footer shows only a subtle status if needed.
- Saved footer shows only a subtle status if needed.
- Admin header shows `Bridge Online` with details.

### Acceptance criteria

- Jobs and Saved pages no longer look like admin dashboards.
- Detailed bridge status remains available in Admin.
- Users are not asked to interpret bridge internals during normal browsing.

## Suggested Implementation Order

1. Jobs row hierarchy and action affordances.
2. Jobs toolbar separation and advanced update placement.
3. Quick filter preset styling and `Customize` rename.
4. Saved Jobs collapsed row and details drawer.
5. Saved Jobs contextual phase override.
6. Saved Jobs activity timeline drawer behavior.
7. Admin advanced/destructive disclosure.
8. Bridge status demotion on user-facing pages.

## Test Plan

- Add focused frontend unit tests where behavior changes, especially save/remove state labels and timeline default scope.
- Add DOM-level checks for Jobs rows to ensure the save/saved icon states and accessible labels are present.
- Add DOM-level checks that `Run Discovery + Fetch + Sync` is not in the primary browsing toolbar.
- Add Saved Jobs checks for guest and empty states so timeline and advanced controls stay hidden by default.
- Add Admin checks that destructive bulk actions are collapsed by default.
- Do a desktop visual smoke pass at the normal packaged-app window size after implementation.

## Non-Goals

- Do not redesign mobile layout in this pass.
- Do not change release version, changelog, tags, or release artifacts.
- Do not add new dependencies.
- Do not solve city-filter data integrity in this plan; that belongs to the release data-quality plan unless a visual component needs defensive display behavior.
- Do not remove Admin functionality; only regroup and de-emphasize high-risk controls.

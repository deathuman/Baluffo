# Scraping Pipeline and Playwright

Overview of the jobs scraping flow, where Playwright is used, and how to compare job counts before and after changes.

## 1) Scraping flow

```text
Discovery (source_discovery)
  -> probe candidates (static/generic_static get optional Playwright fallback on 403/timeout/challenge)
  -> source-discovery-report.json, source-discovery-candidates.json
  -> m5-strategic-backlog.json (derived review snapshot)
  -> pending registry / sync

Pipeline (jobs/pipeline.py -> pipeline_run_setup.py -> pipeline_execution_flow.py -> pipeline_stage_source_execution.py -> pipeline_source_{loop,results,progress}.py -> pipeline_finalize.py)
  -> execute_loader per source (static, scrapy_static, provider APIs, etc.)
  -> Static adapter: listing fetch with optional try_playwright fallback (403/timeout or JS shell + no jobs)
  -> jobs-fetch-report.json, per-source classifications
  -> build_browser_fallback_queue -> jobs-browser-fallback-queue.json

Scrapy path (for scrapy_static sources from browser queue)
  -> registry_entries("scrapy_static") = _scrapy_static_registry_from_browser_queue()
  -> run_scrapy_static_source (static_scrapy.py) invokes scrapers/runner.py with use_browser=True
  -> Runner: Scrapy-Playwright when use_browser and scrapy-playwright installed; else HTTP-only
  -> GenericCareersSpider with meta["playwright"] = True when use_browser
  -> Envelope (jobs, details, stats) back to pipeline; results feed jobs-unified.json
```

- Discovery: Candidates that fail probe (403, timeout, challenge-like HTML) can be retried with Playwright so more sources pass and enter the queue.
- GameDevMap discovery: the default GameDevMap adapter uses the same resumable active-source audit engine as `python src/source_discovery.py --gamedevmap-active-dry-run`. `gamedevmap.activeAuditEnabled` is no longer a supported input; enabled GameDevMap discovery uses the active-audit path instead of the old direct CSV/cache scan. It batches eligible homepages, recovers likely same-site careers URLs in two waves, probes inferred provider/static candidates with bounded concurrency, and writes progress to `data/gamedevmap-active-source-dry-run.json`. Default discovery reuses fresh audit artifacts and feeds validated `jobsFound > 0` rows through the normal candidate/pending/auto-approval flow; static sources do not bypass the admin auto-approve setting. Validated GameDevMap static rows can use the GameDevMap-specific `validatedStaticQueueCap` / `validatedStaticDomainCap` override while still respecting dedupe, tombstones, pending, and auto-approval. The final discovery report includes `gamedevmapAuditSummary` with cache, timing, active split, recovered/browser counts, artifact size, and top failure buckets.
- GameDevMap audit maintenance: the audit artifact includes batch timings plus aggregated failure counts/samples. Use `--gamedevmap-dry-run-batch-size`, `--gamedevmap-dry-run-max-batches`, `--gamedevmap-dry-run-reset`, and `--gamedevmap-dry-run-rerun-reasons` for explicit audit maintenance. Use `--gamedevmap-dry-run-compare-artifact path/to/previous.json` to classify recovered active sources that disappeared between audit runs.
- GameDevMap browser recovery: default GameDevMap discovery stays HTTP-only. Use `--gamedevmap-browser-recovery` to process only saved `browserRecoveryCandidates` from the audit artifact through the existing Playwright fallback helper and merge validated `jobsFound > 0` recoveries back into the same artifact.
- Gameprog/Gamesmap directory audits: enabled Gameprog/Gamesmap adapters use HTTP-only directory audit artifacts by default. `activeAuditEnabled`, adapter `cachePath`, and legacy `cacheTtlMinutes` are no longer supported source-discovery inputs. Gameprog is enabled by default; Gamesmap still requires `gamesmap.enabled=true`. Audit scans run bounded same-site careers recovery on homepage misses before falling back to the legacy weak website-only candidate behavior; set `activeAuditRecoveryEnabled=false` to disable this recovery within the audit path. `activeAuditRecoveryUrlLimit` defaults to `6` recovery URLs per wave, and changing it invalidates the audit signature. Recovery fetch misses are counted as audit diagnostics, not normal adapter failures. The adapters still return the same provider/static/failure rows and route candidates through the normal discovery queue. The final discovery report includes `directoryAuditSummaries` / `summary.directoryAudits` only for audits that ran or reused a fresh artifact in the current process, exposing cache hit, duration, artifact size, timing totals, top failure buckets, adapter boundary counts, and recovery counts such as `recoveryFetchAttempts`, recovered provider/static candidates, recovery failures, and `browserRecoveryCandidates`.
- Sheet-directory audit: enabled sheet-directory discovery uses the shared directory audit artifact. `sheetDirectory.activeAuditEnabled` is no longer a supported input; enabled sheet-directory discovery uses the audit path. The audit records CSV fetch/parse/candidate timings, selected CSV URL, row counts, candidate counts, and failure buckets, then feeds the same provider/static/failure rows into the normal discovery queue. Sheet-directory audits run HTTP-only same-site careers recovery for static sheet rows by default; set `sheetDirectory.activeAuditRecoveryEnabled=false` to disable recovery within the audit path. `sheetDirectory.activeAuditRecoveryUrlLimit` defaults to `6` recovery URLs per wave and is part of the audit signature.
- Seed-careers/web-search audit: enabled seed-careers and web-search stages write/reuse `data/web-search-discovery-audit.json` by default. `webSearch.activeAuditEnabled` is no longer a supported input; enabled seed-careers and web-search stages use the audit path. `webSearch.maxQueries`, `webSearch.maxLinksPerQuery`, and `webSearch.activeAuditRecoveryUrlLimit` tune cached web-search audit work; changing them invalidates the audit signature. The HTTP audit records search/page-fetch timings, sub-stage counts, candidate counts, link diagnostics, bounded query/failure samples, browser-recovery candidates, and failure buckets, then feeds the same provider/static/failure rows into the normal discovery queue. Web-derived audits run HTTP-only same-site careers recovery for successful no-candidate pages by default; set `webSearch.activeAuditRecoveryEnabled=false` to disable recovery. Page-fetch failures and JS-shell pages continue to use existing failure/browser-recovery diagnostics. Use `--web-search-browser-recovery` to process only saved `browserRecoveryCandidates` with the optional browser helper; recovered `jobsFound > 0` rows are written back to the audit artifact as prevalidated candidates for a later normal discovery run.
- M5 review snapshot: Discovery also writes `data/m5-strategic-backlog.json` as a derived review artifact. It is built from the canonical discovery ledger and should not be treated as the source of truth for discovery state.
- Static adapter: Only the listing page fetch per source can use Playwright fallback; detail pages stay HTTP. If the pipeline has Playwright available, it injects `try_playwright` into static loaders.
  Static extraction also runs a shared job-page gate so ordinary pages are rejected as `dead_listing_page` instead of becoming synthetic jobs or generic empty misses.
  Static listing/detail HTTP fetches use the shared redirect-aware cache helper. It can follow one same-site redirect, including `www.`/bare-host aliases and HTTP-to-HTTPS upgrades, but rejects unrelated cross-host redirects, redirect chains, credentialed targets, non-HTTP(S) schemes, and HTTPS downgrades.
  Template or malformed detail links, such as `{{...}}`, known placeholder tokens, and listing-page self-links, are skipped as non-job diagnostics before detail fetch so they do not become source-level fetch errors.
- Dynamic redundant-static suppression: provider coverage validation and static suppression use separate thresholds. One provider success validates that the provider source is real and usable; two consecutive provider successes may skip the linked static source at runtime during normal default fetches with `exclusionReason="dynamic_redundant_provider"`. Suppression can only emit that excluded row when the linked static source is part of the selected/default loader set for the current fetch; a provider can be `ready_later` while suppression remains `0` if the linked static source was not selected. The soak report's `suppressionEligibility.selectionReason`, linked-static fields, and loader identity fields explain this state without force-selecting sources, including cases where a static row is filtered before loader generation by redundant-static rules. For validation only, `python src/jobs_fetcher.py --force-refresh-all --include-linked-static-validation` can include ready linked static rows filtered solely by redundant-static rules so the existing suppression path can emit `dynamic_redundant_provider`; normal default runs remain unchanged. Incremental freshness skips such as `skip_fresh` do not count as provider successes. Explicit `--only-sources` static selection bypasses this skip. Static source rows and `REDUNDANT_STATIC_IF_PROVIDER` are not mutated, and the static source runs again automatically if provider coverage becomes failed, unstable, or needs review.
- Static suppression safety policy: loader selection uses only the latest prior `jobs-fetch-report.json` evidence. Prior `staticSuppressionPolicy` is preferred, with prior `providerStaticOverlap` as fallback. Safe or missing prior evidence allows suppression, `insufficient_history` allows suppression with a warning, and prior `needs_review`, `provider_unstable`, static-only jobs, or `static_only_jobs_detected` pauses suppression so the static source runs normally. Current-run policy and overlap evidence are written for the next run.
- Provider/static overlap audit: completed fetch reports may include read-only `providerStaticOverlap` diagnostics for dynamically suppressed static rows and policy-tracked pairs. The audit uses existing source-state and current `sourceBundle` evidence when available; it does not mutate registry rows or create permanent redundancy rules. Static cleanup remains a separate explicit evidence-backed milestone.
- Redundant static proposals: completed fetch reports may include read-only `redundantStaticProposals` derived from existing `staticSuppressionPolicy`, `providerStaticOverlap`, and `providerCoverage` evidence. Proposals are advisory diagnostics for evaluated provider/static pairs only; they do not change runtime suppression, do not scan unlinked static registry rows, do not create source rows, and do not permit deletion, hiding, demotion, rejection, tombstoning, or permanent source cleanup.
- Dedup evidence: completed fetch reports may include read-only `dedupEvidence` diagnostics built from final canonical rows, `sourceBundle`, and dedup stats. Current-run `mergedCount` / `mergeReasonCounts` can be zero while `sourceBundleCollisionCount` remains nonzero because canonical rows may carry forward historical bundle evidence. This section explains source-bundle outliers, outlier reason counts, URL/source identity shape counts, identity-quality counts, non-provider identity provenance counts, risk reason counts, source-class composition, and risky merge examples such as same title/company across different meaningful locations or weak title/company-only evidence. Outlier reasons distinguish likely multi-location strong-identity bundles, location divergence without strong identity, provider/static disagreement, large unclassified source bundles, and sparse title/company-only bundles. Identity shapes distinguish shared job-detail URLs from shared listing/category URLs, many unique URLs with the same title, provider-ID-backed rows, and missing URL/provider-ID evidence. Identity quality separates provider-grade IDs and shared detail URLs from weaker listing URLs, many-URL non-provider bundles, untrusted non-provider source IDs, and missing identity. Non-provider provenance distinguishes spreadsheet row identity, URL-derived identity, category/directory identity, opaque other-source identity, mixed non-provider identity, and missing provenance. Shared URL evidence is not automatically safe when it looks like a listing/category page or carries category/open-application title caveats, and non-provider source IDs are audit evidence only, not provider-grade dedup identity. `reviewQueueCounts`, `reviewQueueCauseCounts`, and `reviewQueue` provide capped, advisory samples and suspected root causes for operators to inspect before lifecycle UX or dedup behavior changes. Cause classification distinguishes category/department buckets, open-application families, listing-page bundles, non-provider URL identity needing review, parser/directory text pollution, provider/static disagreement, likely legitimate multi-role families, and unknown cases. These diagnostics do not persist review decisions and do not expose merge/unmerge controls. Dedup evidence does not change dedup decisions, lifecycle retention, source selection, or source-policy behavior.
- Source-policy recommendation export: completed fetches may update `source-policy-recommendations.json` in the active output directory. This generated review artifact keeps the latest 10 proposal observations per evaluated provider/static pair and can mark repeated safe evidence as `stable_safe_redundant`, but it does not apply recommendations, alter loader selection, mutate registries or sync state, or make any permanent source-policy change.
- Manual source-policy actions: Admin can record local review state in `source-policy-review-state.json` for evaluated provider/static recommendation pairs. Acknowledged, reviewed, and snoozed states are Admin/Ops visibility only. The only runtime override is `force_pause`, which conservatively pauses dynamic static suppression for that pair; clearing it returns to normal `staticSuppressionPolicy` behavior. There is no force-suppress action, no permanent redundancy rule, and no source row, tombstone, sync state, saved/local data, or `REDUNDANT_STATIC_IF_PROVIDER` mutation.
- Manual migration identity backfill: Admin may explicitly link an existing active/pending supported provider row to an existing static/generic source by writing `migrationSourceIdentity` and Admin-owned link metadata onto the provider row. This is reversible only for links owned by `admin_provider_link_backfill`, does not modify the static row, does not create a permanent redundancy rule, does not mutate `REDUNDANT_STATIC_IF_PROVIDER`, and has no force-suppress behavior. Admin UI controls expose one reviewed apply/clear action at a time; they do not auto-apply, bulk apply, or perform source cleanup.
- Browser fallback queue: Sources classified as `blocked_or_challenge`, `anti_bot_or_challenge`, `rate_limited`, or `needs_review` with `browserFallbackRecommended: true` (and adapter `scrapy_static`) are written to `jobs-browser-fallback-queue.json`. The next pipeline run uses that list as the scrapy_static registry and runs them with Scrapy-Playwright (`use_browser=True`).

## Static source triage

- Preserve registry rows when a static source is no longer viable. Move unsupported static entries to hidden pending with an explicit `pendingReason` instead of deleting them.
- LinkedIn profile/search/post pages and generic third-party aggregators are not viable static career boards. They should stay out of default active fetches unless a supported provider/social adapter owns them.
- Provider-hosted pages should be migrated to an existing provider adapter only when the repo already supports that provider and the source row has enough local evidence to map it safely. Otherwise, hide the static row and document the unsupported provider family as future work.

## 2) Where Playwright is used

| Point | Location | When |
|-------|----------|------|
| Source check (admin) | `src/bridge/source_check_http.py` (`try_fetch_with_playwright`), `source_check_fetch.py` | Admin source check (`trigger_source_check`); optional browser fallback when HTTP fails or page is challenge-like. |
| Discovery probe | `src/source_discovery/probe.py` | Optional fallback for static / generic_static when probe fails with 403, timeout, or challenge-like response; concurrency limited. |
| Static adapter listing | `src/jobs/adapters/static.py` (root surface) and `src/jobs/adapters/static_{runtime,listing,detail,sources}.py` | Optional fallback for the listing page only: on 403/timeout from `fetch_html_cached`, or when HTML looks like a JS shell and no job data is extracted; `try_playwright` is injected by pipeline when Playwright is available. |
| Scrapy-Playwright | `src/scrapers/runner.py`, `src/scrapers/spiders/generic_careers.py` | When scrapy_static sources are run from the browser queue, runner passes `use_browser=True`; if scrapy-playwright is installed, requests are handled by Playwright and the spider sets `meta["playwright"] = True`. If scrapy-playwright is missing, runner falls back to HTTP-only. |

All Playwright use is optional: discovery and pipeline run without Playwright if it is not installed.

## 3) Before and after job count comparison

To see how much the job count changed after scraping improvements:

1. Total jobs: `data/jobs-unified.json` - count the top-level array length (or `keptCount` / output count from the pipeline summary).
2. Browser fallback queue size: `data/jobs-browser-fallback-queue.json` - number of entries (sources that were recommended for browser/Playwright).
3. Per-source status: `data/jobs-fetch-report.json` - for each source: `status`, `fetchedCount`, `keptCount`, `classification`, `error`. Compare counts of `blocked_or_challenge`, `needs_review`, and `ok` / `ok_with_jobs` before and after.
4. Discovery: `data/source-discovery-report.json` - `summary.lossAccounting`, probe failed / low_evidence_skipped; Playwright probe fallback aims to reduce those.

Suggested comparison:

- Before a run: note `len(jobs-unified.json)`, the size of `jobs-browser-fallback-queue.json`, and the number of sources with `classification` in `{blocked_or_challenge, anti_bot_or_challenge, rate_limited, needs_review}` in the last fetch report.
- After a run (with Playwright fallbacks and Scrapy-Playwright enabled): compare the same metrics. Higher unified count, a smaller browser queue, and fewer blocked / needs_review sources indicate improvement.

See also: `docs/DATA_CONTRACT.md` for report shapes and `docs/architecture-ai-map.md` for static adapter and Scrapy path. Saved jobs, local-user data, and active bridge/frontend payload fields remain compatibility boundaries. Internal jobs-fetcher shims such as `pipeline_runtime.py`, `state_source_state.py`, the deleted `static_helpers.py`, `src/jobs/common/contracts.py`, and `src/jobs/reporting.py` are not stable product surfaces; simplify, collapse, or delete them when a slice updates callers and keeps current fetch/report behavior covered by tests.

## 4) Running the pipeline

- Recommended (full fetcher): From repo root, set `PYTHONPATH` to the repo root and run the jobs fetcher module:
  `python src/jobs_fetcher.py` (optionally with `--ignore-circuit-breaker`). This runs all default source loaders including static and scrapy_static.
- npm script: `npm run dev:pipeline` runs the current `src/jobs/pipeline.py` entrypoint with `PYTHONPATH` set to the current directory so that `src` resolves; runtime setup, source execution, task-state helpers, and late-stage report assembly are internal jobs-fetcher implementation details that may be collapsed when the replacement keeps the same active fetch behavior.

## 5) Runtime evidence soak report

Use the source-policy soak report after normal discovery/fetch/Admin usage to summarize whether provider migration, provider coverage, dynamic static suppression, overlap audit, recommendations, review overrides, backup portability, and source-sync cleanliness still agree:

```bash
python scripts/source_policy_soak_report.py --data-dir data --out-dir _out
```

To include an explicit desktop backup payload in the portability check:

```bash
python scripts/source_policy_soak_report.py --data-dir data --out-dir _out --backup-payload path/to/baluffo-backup.json
```

The command writes `_out/source-policy-soak-report.json` and `_out/source-policy-soak-report.md`. It is read-only outside `_out/`: it does not run fetch/discovery, apply recommendations, change loader selection, mutate registries, mutate `REDUNDANT_STATIC_IF_PROVIDER`, or source-sync local review state. Missing first-run artifacts are reported as warnings instead of failures. Failed status is reserved for contract violations such as source-policy review state or recommendation payloads appearing in `source-sync.json`.

The report also includes provider migration activation diagnostics: advisory action counts, staged and pending provider-migration candidates, fetched/validated pending candidates, duplicate/unsupported/insufficient/probe buckets, and active providers that lack `migrationSourceIdentity`. Activation gates are warnings only; they explain why provider staging or validation is dormant without changing runtime suppression, source sync, or registry behavior.

Provider migration staging records blocker diagnostics for every evaluated advisory candidate. Discovery reports expose stageable/staged/skipped counts, blocker buckets such as duplicate active/pending provider, unsupported provider, insufficient evidence, needs probe, provider-row build failure, identity collision, and adapter mismatch, plus compact blocker examples. Strong provider evidence from static-like rows can stage a provider candidate into pending review, but this remains non-destructive: it does not auto-promote, delete, hide, reject, demote, tombstone, mutate static rows, mutate `REDUNDANT_STATIC_IF_PROVIDER`, or apply source-policy cleanup.

The soak report also includes provider coverage link backfill diagnostics. These identify active provider rows that lack `migrationSourceIdentity` but appear to cover static/generic sources through exact redundant-static rules or provider-migration advisory evidence. Ambiguous matches are grouped by provider with each candidate static URL, host, match reason, confidence, blocker, registry state, and source-state history so review can see why a single static source was or was not selected. Exact provider-migration advisory identity remains the strongest disambiguator; source-state history can only resolve a link when one active, non-hidden, non-duplicate static has useful successful history and alternatives are weaker pending/hidden/duplicate/no-history rows. Company-name-only matches are intentionally ignored, and host-only matches without provider-id/rule evidence remain diagnostic. Medium-confidence source-state links are emitted as review-only `needs_review` candidates with an `apiEligible` flag and a ready `apply_migration_identity_link` payload for deliberate manual use; high-confidence exact links keep `backfill_migration_identity_candidate`. The report section is advisory only: it may show high-confidence backfill candidates, source-state-resolved medium-confidence candidates, ambiguous static matches, and blocker examples, but it never calls the API, writes `migrationSourceIdentity`, or changes registry rows.

Admin can expose those review candidates in the Source Policy Review panel and apply or clear one migration identity link at a time through the explicit migration-link bridge action. Medium-confidence candidates require human judgment before applying. The action writes only admin-owned link metadata to the selected provider row, and clear removes only links owned by `admin_provider_link_backfill`; static rows remain unchanged. Admin also keeps linked migration identities visible from current active/pending provider registry state, even when a fresh soak report has moved them out of review candidates and into already-linked evidence, so an admin-owned link remains clearable. One validated provider fetch may not be enough for suppression: dynamic static suppression still requires repeated successful provider fetches. There is no bulk apply, no auto apply, no force-suppress action, no permanent redundancy rule, and no delete/hide/reject/demote/tombstone behavior.

To validate the consecutive-success path manually without waiting for the normal freshness window, apply one reviewed migration identity link, then run two provider-refreshing fetches with the existing force-refresh flag before the soak report:

```bash
python src/jobs_fetcher.py --force-refresh-all --include-linked-static-validation
python src/jobs_fetcher.py --force-refresh-all --include-linked-static-validation
python scripts/source_policy_soak_report.py --data-dir data --out-dir _out
```

Use this only as an operator validation path. It does not lower the runtime threshold, does not make cache skips count as successes, does not mutate registry rows or `REDUNDANT_STATIC_IF_PROVIDER`, and does not change normal default fetch behavior.

For the operator checklist that ties discovery, fetch, soak, Admin migration-link review, forced-refresh validation, source-sync cleanliness, and release-readiness checks together, use [`source-policy-runbook.md`](source-policy-runbook.md).
